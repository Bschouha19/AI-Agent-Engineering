### Chapter 02 research pass — completed 2026-07-11 (pre-draft, run while Chapter 01 was being written)

Targeted research specifically for Chapter 02 ("Reasoning and Planning Patterns — ReAct, Plan-and-Execute, and Reflection"), going one level deeper than the general "ReAct not superseded" finding already recorded above.

- **ReAct mechanics and current guidance**: Confirmed as the Thought → Action → Observation → Thought → ... loop, still current terminology in mid-2026 sources. Best-practice guidance that's new relative to the earlier pass: ReAct's audit-trail transparency (every decision logged as an explicit "thought") is now explicitly called out as a regulated-industry/trust advantage, not just a debugging convenience; defining precise exit criteria (e.g. "verify all citations present, no unsupported factual claims, recommendation is actionable") is cited as measurably improving output quality. Confirmed limitations, consistent with and extending Chapter 01's own termination-failure discussion: latency/token overhead disproportionate for simple tasks, context growth across iterations increasing inference latency, and loop divergence/repetitive-thought risk in poorly-constrained agents — i.e., Chapter 01's "termination failure" category is a directly-cited, current, named risk of ReAct specifically, not just this course's own framing.
- **Plan-and-Execute — current terminology and LangGraph API shape**: Still the dominant name for the pattern; no renaming found. Current structure confirmed as two (or three) node types: a **Planner** node (LLM call that decomposes the task into a multi-step plan), one or more **Executor** node(s) (carry out each plan step, invoking tools, without needing to re-consult the top-level planning LLM after every single action), and commonly a **Replan** node (re-invoked after execution to decide: finish and respond, or revise the plan and continue). In LangGraph terms: a `StateGraph` with a plan-shaped state, `START → planner`, `planner → executor`, `executor → replan`, and a **conditional edge** out of `replan` routing either back to `executor` (continue) or to `END` (done) — this "Plan-Execute-Validate" (PEV) shape, including automated retries and MCP tool integration, appears as a named current pattern and is safe to use as Chapter 02's LangGraph code skeleton. Cited benefit worth including: plan-and-execute reduces LLM calls relative to ReAct for multi-step tasks, since execution of an individual step doesn't require re-consulting the top-level planner each time — a concrete, citable cost/latency tradeoff to pair with Chapter 01's cost table.
- **Reflection / Reflexion — current terminology**: "Reflection" (generate → critique → revise loop) is the actively-used current umbrella term in 2026 sources; "Reflexion" specifically still refers to the named pattern of augmenting reflection with **explicit persisted memory of past failures/successes** (an agent generates a text "reflection" summary after an episode and retrieves it in future similar tasks) — so Reflexion is best framed as reflection-plus-episodic-memory, not a synonym for reflection generally, and this is a good forward link to Chapter 04 (Agent Memory Systems). Two implementation patterns confirmed as current and distinct: **single-model reflection** (same LLM does generation and critique via different prompts — cheapest, simplest) versus **dual-role reflection** (separate Writer/Critic agents/roles, repeating until a quality threshold is met — Google's ADK is cited as supporting this natively via "loop agents"). No specific numeric guidance on optimal reflection-iteration count was found in these results; treat "how many reflection passes" as a cost/quality tuning decision the chapter should present as a tradeoff (citing Chapter 01's cost-multiplier table) rather than citing a specific recommended number, since no source gave one.
- **Emerging/dominant patterns beyond the three named in the chapter title**: **Tree of Thoughts (ToT)** and **Graph of Thoughts (GoT)** are both confirmed current (2026) named patterns, positioned as a step beyond linear ReAct/Chain-of-Thought reasoning for tasks with branching or interdependent reasoning paths (math problem-solving, strategic planning, game play, theorem proving, constrained multi-step planning). ToT's current described shape: a proposer (generates candidate next-step moves), an evaluator (scores each branch), a search policy (beam search or BFS are both cited), a pruning rule, and a stopping condition (solution found or depth limit hit). GoT generalizes further to an arbitrary directed graph of thoughts (branches can merge/recombine, not just split) for problems ReAct/ToT's linear-or-tree structure doesn't fit well. **Recommendation for the chapter**: cover ToT/GoT as a "beyond the big three" section or Technology Comparison row rather than a fourth core pattern on par with ReAct/Plan-and-Execute/Reflection, since the chapter's own title and COURSE_INDEX.md Key Skills scope it to exactly those three — but they are clearly citable as the current state of the art one level up in reasoning-pattern sophistication, and are worth at least one paragraph plus a Mermaid diagram contrast.
- **Reasoning/planning-specific evaluation, distinct from end-to-end task success (relevant to Chapter 02 self-assessment content and a forward link to Chapter 12)**: Confirmed as a real, current, named distinction — the "Agent Planning Benchmark (APB)" is a 2026 planning-specific diagnostic benchmark (4,209 multimodal cases, 22 domains, 5 settings including robustness under broken/extraneous tools and unsolvable tasks) built specifically because end-to-end success alone can't tell you whether a failure was a planning failure or an execution failure. Trajectory-evaluation metrics confirmed as currently used to isolate reasoning/planning quality specifically: step efficiency, argument correctness, tool correctness, plan adherence, plan quality, and reasoning coherence/step-level faithfulness — these are good candidate metric names for Chapter 02 to introduce conceptually (with the full evaluation *methodology* correctly deferred to Chapter 12, per this course's existing chapter boundaries).

**Not fully resolved / flag for an explicit hedge if cited specifically in the chapter**: no source in this pass gave a specific, citable numeric recommendation for reflection-pass count, nor a single authoritative "current state of the art beyond ToT/GoT" claim (search results characterized ToT/GoT themselves as the current frontier, not something newer superseding them) — both are fine to write as general current framing, but should not be written as a specific vendor- or paper-attributed numeric best practice unless a specific chapter draft finds a stronger source at write time.

### Chapter 03 research pass — completed 2026-07-11 (pre-draft, run while Chapter 02 was being written)

Targeted research for Chapter 03 ("Tool Use and Function Calling at Scale"), covering the agent-consuming-side complement to Volume 2's tool-serving-side content: tool selection at scale, parallel tool calls, error recovery, result validation, the function-calling-specific benchmark, and the current MCP spec's scale-relevant mechanics.

- **Tool selection at scale / "too many tools" problem**: Confirmed as a real, current, named problem with concrete numbers. A well-documented tool typically costs 500–1,500 tokens; loading ~200+ tool definitions upfront can exceed a model's context budget outright, and accuracy is reported to measurably decline once an agent is choosing from roughly 20–25+ tools loaded simultaneously — this is a *decision-quality* problem, not just a token-cost one, directly extending Chapter 01's tool-use-failure taxonomy category. **Progressive disclosure** is the confirmed current named pattern: don't send every tool schema on every call; let the agent discover/fetch full schemas on demand. Production numbers cited: 85–100x token reductions are reported by named production implementations. **Directly citable, high-value finding**: Anthropic shipped exactly this as a first-party feature — the **Tool Search Tool** (announced 2026-01-14, per Anthropic's own "Introducing advanced tool use on the Claude Developer Platform" post), where tools are marked `defer_loading: true` and the agent searches for and loads only the 3–5 most relevant tools into context per turn, with Anthropic reporting an 85% context-token reduction (~191,300 tokens preserved vs. ~122,800 with the traditional load-everything approach). The Claude Agent SDK's own current docs page ("Scale to many tools with tool search") confirm this is **on by default** in the SDK, with the stated guidance that manually disabling it only makes sense below ~10 tools. **This is worth flagging explicitly in the chapter**: this is the same mechanism this course's own authoring tool (Claude Code, via a "ToolSearch" tool) visibly uses in practice — a good, concrete, verifiable "you're already using this pattern" hook for the chapter's Real-World Analogy or opening motivation.
- **Parallel tool calls — current Claude API mechanics**: Confirmed current and unchanged in spirit from Chapter 01's single-tool-call code: a single assistant turn with `stop_reason: tool_use` can contain **multiple `tool_use` blocks**. The API does not prescribe execution order — official Claude docs explicitly say the caller may run them concurrently (e.g. `asyncio.gather`), sequentially, or a mix, with the stated guidance that independent read-only tool calls are good parallel-dispatch candidates and tools with side effects/shared state/ordering requirements are safer run sequentially. All results must come back as one `tool_result` per `tool_use` block in the next user message, matched by `tool_use_id`, with every `tool_result` block preceding any text content in that message — mixing up IDs across concurrent calls is called out as a common, concrete bug. This maps directly onto a "the model requests parallel work, your orchestrator decides how literally to parallelize it" architecture point worth making explicit in the chapter.
- **Tool-call error recovery at scale**: Confirmed current, extends Chapter 01's transient-vs-structural retry distinction with two scale-specific patterns. **Circuit breakers**: a named, current pattern — closed/open/half-open state machine per tool, so a chronically-failing tool fails fast (and the model is explicitly told the tool is unavailable) instead of every call in a batch re-paying a timeout; multi-agent/parallel deployments need a *shared* breaker store (e.g. Redis-backed or a reducer in shared graph state), not one breaker per isolated call path. **Partial-failure handling for parallel batches**: when N of M parallel tool calls fail, the orchestrator has to decide whether the surviving N results are usable or the whole batch needs a retry — explicit current guidance (paraphrased, not a direct quote): an agent that answers from 3 of 4 data sources *and says so* is more trustworthy than one that silently fills the gap with a hallucinated value. This is a good direct extension of Chapter 01's "unambiguous tool result" rule to the batch case.
- **Tool result validation**: Confirmed as a named, current, three-layer pattern distinct from (but related to) Chapter 01's tool-call-injection security concern: **schema validation** (typed contract — does the shape match what's expected), **structural validation** (is it parseable at all), and **content/business-rule validation** (is it plausible/correct given domain rules, e.g. "this returned value violates a known constraint"). Current sources frame this as increasingly load-bearing because structured-output-chaining (one tool/step's JSON output feeding directly into the next step's input) is now described as the default agent pattern in 2026, meaning an unvalidated malformed or semantically-wrong result doesn't just mislead the model narratively — it can crash or corrupt the very next mechanical step. Tool-call injection (Chapter 01) is about *malicious/adversarial* content in a tool result; this is about *malformed or semantically-wrong-but-non-adversarial* content — worth drawing that line explicitly in Chapter 03 rather than re-explaining injection from scratch.
- **Function-calling benchmark (distinct from end-to-end agent benchmarks)**: The **Berkeley Function-Calling Leaderboard (BFCL)** is confirmed current and still the standard function-calling-specific benchmark as of mid-2026, now at **BFCL V4** (progression: V1 single-turn Feb 2024 → V2 live enterprise data Aug 2024 → V3 multi-turn Sep 2024 → V4 holistic agentic evaluation, July 2025), with the leaderboard itself last updated July 2026. Leading scores cited are inconsistent across sources found (one source cites Llama 3.1 405B Instruct leading V4 at 0.885; another cites a V3 single+multi-turn leaderboard led by GLM-4.5 at 77.8%) — **flag this as needing a direct leaderboard check (gorilla.cs.berkeley.edu/leaderboard.html) at actual chapter-draft time rather than citing either specific number here**, since the two figures come from what appear to be different leaderboard views/versions and weren't reconciled in this pass.
- **MCP spec currency, scale-relevant mechanics**: Confirmed current finalized MCP spec version is **2025-11-25**; a **2026-07-28 spec is a release candidate** (not yet final as of this research date) that specifically targets scale — per the MCP blog, the RC lets `tools/list` responses be cached by clients for as long as the server's `ttlMs` permits, and list endpoints (`tools/list`, `resources/list`, `prompts/list`) no longer vary per connection, enabling a remote MCP server to sit behind a plain round-robin load balancer. `tools/list` has supported **cursor-based pagination** for a while (confirmed still current) — directly relevant once a single MCP server exposes "dozens of tools." Tool *namespacing* specifically was not confirmed as a first-class current spec mechanism (searches did not surface one) — production teams are instead using an informal **"MCP Wrapper Pattern"** (expose only discovery/search tools, not the full toolset, at the top level) and dynamic/progressive loading as the practical current workaround, which ties directly back to the Tool Search Tool finding above. Production-scale numbers worth citing: a typical production agent by Q1 2026 was reported connecting to 5–20 MCP servers, each exposing roughly 5–50 tools — i.e., "hundreds of tools total" is now a normal, not exceptional, production shape, which is the strongest concrete motivation for this whole chapter.
- **Current API accuracy for code examples**: Confirmed accurate for chapter code: (1) Claude API parallel tool use — multiple `tool_use` blocks in one response, `asyncio.gather` or sequential dispatch both valid, `tool_result` blocks matched by `tool_use_id`, ordered before any text in the reply message; (2) Claude Agent SDK (`claude-agent-sdk` v0.2.115, version already confirmed in the prior pass) — `allowed_tools`/disallowed-tool lists operate as a distinct layer from the `tools` option (which controls what appears in context at all) for approving/denying attempted calls; Tool Search is **on by default** in the SDK; official current guidance is explicit least-privilege scoping — pass only the tool set relevant to the current session's actual task/tenant, not the union of everything the system supports.

**Not fully resolved / flag for an explicit hedge if cited specifically in the chapter**: the two BFCL leaderboard-leader figures found in this pass (Llama 3.1 405B at 0.885 on what's described as V4; GLM-4.5 at 77.8% on what's described as a V3 single+multi-turn view) were not reconciled to a single authoritative current number — re-check the live leaderboard directly at chapter-draft time rather than citing either figure as *the* current BFCL leader. MCP tool *namespacing* as a formal spec-level mechanism (as opposed to an informal production workaround pattern) was not confirmed — do not describe namespacing as a spec feature; describe the Wrapper Pattern and dynamic loading as the current practical workaround instead.

### Chapter 04 research pass — completed 2026-07-11 (pre-draft, run while Chapter 03 was being written)

Targeted research for Chapter 04 ("Agent Memory Systems — Working, Long-Term, and Episodic Memory"), which needs to close the loop Chapter 02 deliberately left open (Reflexion's persisted-memory layer) and reuse Volume 3 Ch06's Dense Retrieval for memory retrieval specifically.

- **Mem0 current API and architecture**: Confirmed current. Install via `pip install mem0ai`; the hosted-client pattern is `from mem0 import MemoryClient; client = MemoryClient(api_key=...)`, then `client.add(messages, user_id="user123")` (a list of role/content dicts, same shape as a chat transcript) and `client.search("query text", user_id="user123")`. By default Mem0 does **inferred extraction** — it runs the raw conversation through an LLM to distill discrete, structured memories rather than storing the raw transcript verbatim (`infer=False` stores raw messages if that's genuinely wanted instead). Confirmed differentiation over "roll your own vector DB similarity search": automatic memory extraction/consolidation from conversation, conflict resolution between contradictory memories, and built-in scoping by `user_id`/`agent_id`/session — i.e. Mem0's value-add is the extraction-and-consolidation pipeline in front of the store, not the vector search itself. Status: 59,600+★, Apache 2.0, v2.0 released June 2026, described by multiple sources as "the de facto standard for agentic memory" — consistent with and updating this repo's kickoff-research one-liner. (One source cited a lower, likely-stale ~48,000★ figure — treat 59,600+ as the more current number, but re-confirm star count directly at chapter-draft time since it's a moving target by definition.)
- **Named alternatives — Letta (formerly MemGPT) and Zep**: Both confirmed active in 2026, not deprecated, but positioned differently from Mem0 and from each other. **Letta** carries the original MemGPT "OS-inspired" framing forward literally — main context window as RAM, archival memory as disk, with the agent itself managing what gets paged in/out via memory tools over a REST API; current center of gravity has shifted toward "Letta Code" (42.5% on Terminal-Bench, positioned as the #1 model-agnostic open-source agent), with tiered pricing (free/​Pro $20/mo/​Enterprise) as of June 2026. Best fit: long-running, stateful agents where the agent should manage its own memory allocation, not just retrieve from an external store. **Zep** differentiates specifically on **temporal reasoning over facts that change over time**, via its Graphiti knowledge-graph engine — cited at 63.8% on LongMemEval (GPT-4o) vs. Mem0's 49.0% on the same benchmark, a concrete, citable number for a Technology Comparison row. Caveat: Zep's managed **Community Edition has been deprecated**; production Zep now means Zep Cloud or a self-run Graphiti deployment, not the free managed tier that may appear in older tutorials — worth flagging so the chapter doesn't point readers at a discontinued free tier.
- **Memory taxonomy currency check**: Current 2026 sources converge on a **four-part** functional taxonomy, not the three-part split implied by this chapter's title alone: **working/in-context memory** (the active context window — "what am I doing right now"), **episodic memory** (records of specific past events/interactions/decisions), **semantic memory** (accumulated factual knowledge — user profile fields, policies, product config), and **procedural memory** (skills, rules, playbooks that evolve with experience). The explicit design principle repeated across sources: these have different lifecycles and epistemic status, and collapsing them into one representation loses real distinctions. **Recommendation for the chapter**: keep the title's three named categories (Working, Long-Term, Episodic) as the chapter's primary teaching structure per its committed scope, but explicitly note within "Long-Term Memory" that current practice further splits it into semantic (facts) and procedural (learned behavior) sub-types — don't present the three-way title split as if it's the only or most granular current taxonomy, since that would understate what's actually current.
- **Memory consolidation / promotion, current guidance**: Confirmed current, concrete, and citable. Dominant production pattern is **three-tier hierarchical memory**: a hot layer (last ~10 turns, verbatim, uncompressed), a warm layer (turns ~11–40, maintained as a rolling detailed summary of key decisions/tool outputs/task state), and a cold layer (everything older, compressed to high-level goals/constraints/major findings). **Anchored iterative summarization** (merging new content into a persistent running summary) is confirmed to outperform full-reconstruction summarization (regenerating the whole summary from scratch each time) on accuracy/completeness/continuity. Confirmed current promotion cadence guidance: consolidate at session end for user-intent signals, daily for conversation summaries, weekly for semantic distillation of accumulated episodic records — a concrete, citable answer to "when does something get promoted from working to long-term memory," useful for this chapter's Production Architecture section.
- **Memory retrieval scoring, distinct from plain RAG similarity**: Confirmed as a real, current, and still-dominant pattern, tracing to the original "Generative Agents" (Stanford "simulacra town") paper and explicitly described as having been adopted by virtually every subsequent memory system since (MemGPT, Mem0, LangGraph-based memory implementations all cited as using it). The formula: `score = α·recency + α·relevance + α·importance`, each component min-max normalized to [0,1] before summing — **recency** as exponential decay since last access (paper's constant: γ=0.995/hour), **relevance** as cosine similarity between the query embedding and the memory's embedding (this is the direct Volume 3 Ch06 Dense Retrieval connection), and **importance** as an LLM-assigned 1–10 rating captured at write time (a mundane observation scores low, a significant decision/commitment scores high). **This is the chapter's strongest, most concrete technical payload**: memory retrieval is RAG's dense retrieval *plus* two additional, well-established scoring terms RAG normally doesn't need, and the chapter should teach this formula explicitly rather than treating memory retrieval as "just RAG again."
- **Memory-specific failure modes**: The generic CLAUDE.md template issue ("long-term memory grows unbounded → context window exhaustion or irrelevant retrieved memories dominate") is confirmed still accurate and current, and can now be grounded in the specific, current hierarchical-memory/consolidation-cadence guidance above as the concrete fix rather than staying purely abstract. A second, distinct and worth naming explicitly: **memory poisoning** — confirmed as a named, current, and structurally distinct threat from prompt injection specifically because of persistence: "prompt injection ends when the session ends, but memory poisoning persists when an attacker writes a malicious instruction into the agent's long-term memory store so every subsequent session starts with that instruction already loaded." Good, sharp, citable distinction for this chapter's security preview.
- **Memory security/privacy preview**: Confirmed as a real, current, *named* concern specific to agent memory (not just generic data-privacy carryover from earlier volumes) — "tenant bleed-through" (retrieval filters/vector metadata/application caches failing to enforce a user or tenant boundary) and "memory contamination" (one session's facts later retrieved as valid context for a different user) are both named current failure modes.
